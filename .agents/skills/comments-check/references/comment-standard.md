# 可噜记账注释标准

## 合格函数注释

函数注释至少回答：

1. 这个函数给用户或系统带来什么结果？
2. 输入数据是什么，单位和限制是什么？
3. 返回什么，失败时怎样表示？
4. 是否会修改数据库、文件、界面状态或其他外部内容？
5. 哪条产品规则使它必须这样实现？

不是每个函数都需要写齐五项；只写与该函数真实行为相关的内容。

### 好示例

```ts
/**
 * 把用户输入的人民币元转换为数据库保存的整数分。
 * 只接受大于 0 且最多两位小数的金额；无效输入返回 null，调用方据此阻止保存。
 * 使用整数分可以避免 0.1 + 0.2 这类小数计算误差影响账目。
 */
function parseAmountToCents(input: string): number | null {
  // ...
}
```

它说明了用途、限制、失败结果和设计原因，小白不需要先理解浮点数实现细节。

### 差示例

```ts
// 转换金额
function parseAmountToCents(input: string): number | null {
  // 判断输入
}
```

它只是重复函数名和代码动作，没有说明单位、限制、失败结果或原因。

## 合格核心代码注释

核心代码段注释重点解释决策和风险：

```ts
// 先在新位置创建完整快照并核对账目、分类和设置数量。
// 只有三类数据都一致才切换路径，避免迁移中断后应用打开半份数据库。
```

不要写：

```ts
// 创建快照
// 判断数量
// 修改路径
```

## 一致性核对清单

- 金额究竟是元还是分；是否允许 0、负数或三位小数。
- 日期使用本地时间还是 UTC；统计月份如何确定。
- 函数失败时抛错、返回空值还是显示提示。
- 数据库操作是否在事务中；失败是否整体回滚。
- 备份包含哪些表；恢复前是否保留当前数据。
- 分类停用、改名和删除对历史账目的真实影响。
- 数据迁移何时切换路径，原数据库是否保留。
- 预加载接口允许界面访问哪些本机能力。

## 小白可读性分级

- **清楚**：不看实现也能理解用途、输入、结果和原因。
- **基本清楚**：能理解用途，但缺少单位、失败行为或影响说明。
- **难懂**：大量使用 IPC、事务、约束、序列化等术语却不解释。
- **误导**：阅读后会对真实代码行为产生错误理解。

## 注释密度规则

- 目标是每 10 行有效内容中至少约 3 行有效注释，即注释密度不低于 30%。
- 空行、只有括号的行和自动生成文件不用于证明覆盖率。
- 行尾注释不重复计为独立注释行。
- 许可证头、整页重复说明、被注释掉的旧代码和无意义复述不算有效注释。
- 同一段高质量注释可以解释紧随其后的一个完整核心步骤，不要求每行代码都有注释。
- 总密度只是底线；每个函数和每段重要核心代码仍需单独检查。

## 问题严重度

- **严重**：错误注释可能导致金额错误、数据丢失、隐私泄露或安全边界被破坏。
- **重要**：核心函数或关键步骤缺少说明，或注释与行为明显不符。
- **一般**：注释基本正确但小白难懂，或局部密度不足。
- **建议**：表达可以更清晰，但不会误导维护。
